# Автоматическая турнирная таблица после подписания протокола

## Поведение

Успешный ответ на подписание протокола означает, что результат и соответствующая таблица уже сохранены. Отдельный запрос пересчёта после каждого матча больше не нужен.

- Онлайн: `finished` у сессии ещё не является подписью. Матч учитывается после `protocol_signed`. Это правило применяется также к ручному пересчёту, межгрупповому сравнению и исходным данным отбора.
- Ручной ввод: результат попадает в таблицу при подписании обычного или технического протокола. Отсутствие онлайн-сессии либо `not_started` после сброса не исключает такой результат.
- Исправления завершённого подписанного протокола: добавление/отмена гола пересчитывают счёт, очки и показатели; карточки пересчитывают дисциплинарные показатели тай-брейков. Счёт сохранённой онлайн-сессии также синхронизируется с исправленным результатом.
- Пересчёт строит таблицу заново по подписанным результатам, не прибавляет очки к предыдущему значению.
- В обычном случае обновляется только группа/этап затронутого матча. Плей-офф не учитывается как круговой турнир. Поддерживается старый круговой турнир без этапов.
- Если после публикации новой версии правил в таблицах осталась другая версия, ближайшее подписание/исправление пересчитает таблицы турнира целиком. Без новых протоколов организатор может выполнить полный пересчёт сразу после публикации правил.
- Ручные ранги решения/жребия сохраняются. `NULL` не трактуется как действительный ранг. Отдельные очки за техническую победу/поражение учитываются при наличии соответствующих настроек.

## Целостность и параллельные запросы

Подпись, результат, связанные изменения дисциплины и пересчёт выполняются в одной транзакции. При ошибке пересчёта подпись или исправление не сохраняются частично. Онлайн-квитанция запроса записывается в той же транзакции; повтор принятой команды с тем же UUID не удваивает результат.

Запись результатов и пересчёт используют общую блокировку турнира `pg_advisory_xact_lock(78203, tournamentId)` до блокировки строки матча. Для пересчёта используется `READ COMMITTED`: второй ожидавший запрос видит результат первого. Порядок согласован с изменением календаря и публикацией правил. Полный ручной пересчёт тоже атомарный. Публичный многоэтапный read-model читается в `REPEATABLE READ`, чтобы не смешивать версии таблиц и матчей между несколькими запросами.

Ручные события принимают необязательный `clientEventId`. Редактор повторяет тот же идентификатор при повторной отправке неизменённого события после ошибки в открытой форме. Сервер возвращает уже созданное событие без повторного изменения счёта/карточек. Изменение параметров того же UUID отклоняется. После перезагрузки формы перед новым вводом следует сверить события сервера: долговременная офлайн-очередь ручного редактора не добавлялась.

Административный пересчёт требует авторизации и права редактирования конкретного турнира. Ручные подписи/события и исправления также проверяются в контексте сообщества матча. Публичное чтение таблицы остаётся доступным без авторизации.

## Проверенные риски

| Случай | Ожидаемый результат |
| --- | --- |
| Матч запущен, приостановлен или только завершён без подписи | Не влияет на таблицу |
| Обычная онлайн-подпись | Таблица готова до успешного ответа |
| Повтор онлайн-подписи с тем же UUID | Нет повторного начисления очков |
| Ручной протокол, автогол, техническое поражение | Корректный результат и очки после подписи |
| Добавление/отмена гола в подписанном протоколе | Новые счёт, победитель/ничья и очки; одна сыгранная игра |
| Добавление/отмена карточки | Новые дисциплинарные баллы, без двойного изменения счётчиков игрока |
| Повтор ручного исправления с тем же UUID | Одно событие, один результат |
| Отказ записи таблицы | Откат подписи/исправления, событий, счёта и изменений дисциплины |
| Два одновременных подписания одной группы | Учитываются оба матча, нет потерянного обновления |
| Другая группа/другой турнир | Не меняются при обычном обновлении |
| Изменённая опубликованная версия правил | Все таблицы турнира приводятся к одной версии |
| Ручные ранги и пустые nullable-поля | Ранги сохраняются, `NULL` не ломает сортировку |
| Матч плей-офф | Не добавляется в групповую таблицу |
| Смена победителя уже продвинутого матча плей-офф | Существующая защита отклоняет небезопасное исправление; транзакция откатывается |
| Гол в техническом результате/матче с дополнительным временем или пенальти | Обычное исправление счёта отклоняется существующей проверкой |

Регрессии находятся в `match-continuity.integration.spec.ts` (только изолированная PostgreSQL), `signed-match-results.spec.ts`, тестах движка/сервиса таблицы и прав доступа. Повтор ручного запроса проверяется браузерным тестом `match-result-retry.spec.ts`.

## Границы изменения

- Утверждённые снимки отбора и состав уже сформированной сетки не переписываются автоматически при исправлении группы. Для изменения спортивного решения остаётся явный пересмотр отбора с предварительным сравнением. Проверка устаревшего предварительного отбора по хешу исходных данных сохранена.
- Новый механизм обновляет таблицу на сервере. Уже открытая страница в другом браузере получает новое состояние при следующей загрузке/запросе; WebSocket-рассылка не добавлялась.
- Прямые SQL-изменения, сторонние записи в таблицы, ручное изменение чисел материализованной таблицы обходят сервисные операции. После них необходим административный пересчёт. Штрафные очки не следует вносить напрямую в вычисляемые строки; полноценное применение журнала административных решений этой задачей не реализуется.
- Новая миграция для этой функции не нужна. На ВМ требуется обновить бэкенд и фронтенд. Рабочая БД при разработке не изменялась.
- Старые уже сохранённые таблицы не пересчитываются массово при запуске сервера. Для немедленного исправления исторически устаревших таблиц нужен один административный пересчёт; далее подписи/исправления обновляют их автоматически.
