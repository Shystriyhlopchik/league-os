# Сообщества, участники и права

Подача/рассмотрение заявок и назначение администратора отдельного турнира
описаны в [инструкции по заявкам](tournament-applications.md).

Раздел кабинета: `/dashboard/communities`. Учётная запись общая для платформы;
роли сообщества хранятся отдельно от глобальных `user_roles`.

## Полномочия

| Роль | Доступ |
| --- | --- |
| Суперадминистратор платформы (`super_admin`) | Создаёт сообщества, назначает владельцев, управляет всеми сообществами |
| Владелец сообщества (`owner`) | Добавляет участников, назначает и отзывает администраторов; управляет турнирами своего сообщества |
| Администратор сообщества (`admin`) | Просматривает участников; создаёт серии соревнований, сезоны и турниры; управляет турнирами своего сообщества |
| Участник сообщества (`member`) | Не получает административных полномочий; может получить отдельное назначение организатором/наблюдателем турнира |

Владелец сообщества не может назначать других владельцев или менять их права:
это действие выполняет суперадминистратор платформы или оператор сервера.
Последнего активного владельца нельзя удалить или понизить даже через API
суперадминистратора. Изменения членства сериализуются блокировкой строки сообщества.

Делегированный организатор имеет существующие права чтения/редактирования турнира,
наблюдатель — чтения. Оба должны оставаться активными участниками сообщества.
Назначение организаторов остаётся в существующем API турниров, отдельный интерфейс
для него в этой версии не добавлен. Конструктор в кабинете доступен владельцам,
администраторам сообществ и суперадминистраторам платформы.

## Обновление работающей установки

Перед обновлением сохраните резервную копию БД по инструкции README.
Из корня репозитория выполните обычный production-деплой:

```bash
docker compose --env-file .env -p league-os-prod \
  -f infrastructure/docker/docker-compose.prod.yml up -d --build --remove-orphans

docker compose --env-file .env -p league-os-prod \
  -f infrastructure/docker/docker-compose.prod.yml logs migrations
```

Миграция `1792454400000-communities`:

- создаёт «Дворовую лигу» (`dvorovaya-liga`);
- закрепляет за ней все существующие `competitions`, а через них — сезоны и турниры;
- добавляет действующих глобальных суперадминистраторов владельцами сообщества,
  глобальных администраторов — администраторами сообщества;
- добавляет прежних владельцев и участников турниров в сообщество, прежним
  владельцам сохраняет отдельное назначение организатора;
- записывает начальные назначения в журнал с источником `migration`.

Это перенос существующей однообщинной установки. Если в базе уже находятся
несколько независимых организаций, перед деплоем нужна отдельная таблица
сопоставления соревнований и их сообществ: автоматический перенос объединяет их.

Глобальные роли не удаляются. Старый глобальный `admin` продолжает давать права
в старых разделах (команды, протоколы, трансферы, новости). Назначение через новую
страницу **не выдаёт эту глобальную роль**. После отзыва местных прав глобальный
администратор всё ещё имеет свои прежние глобальные полномочия, но не получает
обход новых проверок турниров. Перед использованием платформы несколькими
независимыми организациями старые глобальные роли и разделы нужно мигрировать
отдельно; эта версия не является полной изоляцией всей платформы.

## Назначение первого владельца

Если суперадминистратора нет, оператор сервера назначает владельцем уже
зарегистрированного пользователя по **точному логину**. Команда не создаёт
учётные записи и не выдаёт глобальные права.

```bash
docker compose --env-file .env -p league-os-prod \
  -f infrastructure/docker/docker-compose.prod.yml \
  run --rm --no-deps migrations npm run community:owner -- \
  --community dvorovaya-liga --user EXACT_USERNAME
```

Для локальной установки из `league-os-backend` с настроенными переменными БД:

```bash
npm run migration:run
npm run community:owner -- --community dvorovaya-liga --user EXACT_USERNAME
```

Повторный запуск команды для действующего владельца ничего не меняет. Назначение
фиксируется в журнале с источником `server-command`.

## Выдача и отзыв прав

1. Владелец открывает «Сообщества · участники и права» в `/dashboard`.
2. Выбирает сообщество и находит пользователя по точному логину или email.
   Поиск возвращает только ФИО, логин и идентификатор, без email, телефона и
   данных авторизации.
3. Добавляет участника или назначает администратора, подтверждая имя и сообщество.
4. Новый администратор обновляет страницу и открывает раздел «Сообщества».
   Там доступны создание серии соревнований/сезона и переход к конструктору.
5. Для отзыва используется «Отозвать права» (переход в участники) либо «Исключить».

Отзыв/исключение также удаляет отдельные назначения на турниры этого сообщества.
Историческое `owner_user_id` в турнире остаётся сведением о создателе и больше
не даёт самостоятельного доступа. Роли читаются из БД при каждом запросе;
ожидать истечения JWT или требовать повторного входа не нужно. Уже начавшийся
запрос может завершиться, новые запросы проверяют обновлённое членство.

Пользователь в другом сообществе сохраняет свои роли. Глобальная блокировка
аккаунта, роли игрока/капитана и выступления за команды этой операцией не меняются.

## API

Все перечисленные методы требуют JWT, полномочия проверяются сервером.

- `GET /api/communities` — свои сообщества; суперадминистратору доступны все.
- `POST /api/communities` — создание суперадминистратором: `name`, `slug`, `ownerUserId`.
- `GET /api/communities/:id/members?search=&role=&page=1&limit=20` — участники.
- `GET /api/communities/:id/user-search?search=EXACT_LOGIN_OR_EMAIL` — поиск для владельца.
- `PATCH /api/communities/:id/members/:userId` — `{ "role": "admin" }` либо `member`;
  `owner` разрешён только суперадминистратору.
- `DELETE /api/communities/:id/members/:userId` — прекращение членства.
- `GET /api/communities/:id/audit?page=1&limit=20` — журнал для владельца.
- `GET /api/communities/:id/context` — серии, сезоны и турниры для управления.
- `POST /api/communities/:id/competitions` — `name`, `slug` (уникальный на платформе).
- `POST /api/communities/:id/seasons` — `competitionId`, `name`, `slug`, `year`.

Турнир наследует сообщество через `season → competition → community`.
`POST /api/tournaments` проверяет права в сообществе сезона; необязательный
`communityId` дополнительно проверяется на соответствие сезону. Перенос турнира
в сезон другого сообщества запрещён. Публикация и конструктор сохраняют
существующий флаг `TOURNAMENT_BUILDER_ENABLED`.

## Границы этой версии

Реализовано управление доступом к сообществам и жизненному циклу турниров.
Общие составы команд, трансферы, статистика, новости и старые экраны ручного
ввода результатов пока не переведены на права сообщества. Местный администратор
не получает к ним глобальный доступ. Каталог команд остаётся общим.

На новой установке сначала выполните миграции и `npm run seed`, зарегистрируйте
пользователя, затем назначьте первого владельца серверной командой. При откате
код и схему нужно согласовывать: удаление миграции удаляет сообщества и их журнал.
