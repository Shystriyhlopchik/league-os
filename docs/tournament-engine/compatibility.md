# Стратегия обратной совместимости

## Цель

Ввести многоэтапную модель без одномоментного изменения текущих страниц, API и данных. Переход выполняется по схеме expand → migrate → switch → contract.

## 1. Expand

Добавляются nullable-ссылки и новые таблицы, не удаляя:

- `tournaments.format` и существующий status;
- `tournament_teams.groupName`, `seedNumber`;
- `matches.round`, `homeScore`, `awayScore`;
- уникальность/данные старой `standings` до появления нового read model;
- `player_tournament_stats` до переноса наказаний.

Старые write paths продолжают работать в legacy mode.

## 2. Bootstrap legacy profile

Для каждого существующего турнира создаются:

1. владелец/legacy policy;
2. один этап, тип которого выводится из `format`;
3. rule version v1 из [current-league.json](./examples/current-league.json) с подтверждёнными продуктовыми параметрами;
4. stage participants из `tournament_teams`;
5. ссылки старых матчей на этап и v1.

Если `groupName` заполнен, миграция сначала формирует уникальные группы и только затем назначения команд.

## 3. Dual read и dual write

Переходный application layer:

- новые API читают stage-aware данные;
- старые API получают адаптированный плоский ответ;
- новый write path заполняет новые поля и временно поддерживает legacy-поля;
- сравнение старого и нового расчёта запускается в shadow mode.

Различия таблиц, статистики и дисциплины логируются и блокируют переключение конкретного турнира.

## 4. Switch

Feature flags включаются по турниру:

- `tournament_engine_v1_write`;
- `tournament_engine_v1_public_read`;
- `tournament_engine_v1_builder`.

Сначала переводится тестовый турнир, затем текущая лига, затем пользовательское создание.

## 5. Contract

Старые поля и endpoints удаляются только после:

- миграции всех активных турниров;
- подтверждённого совпадения расчётов;
- отсутствия legacy clients;
- завершения минимум одного полного сезона на новой модели;
- отдельной миграции и плана отката.

## Профиль текущей лиги

Пример фиксирует только поведение, доказуемое по текущему коду:

- один `round_robin` этап;
- `3/1/0`;
- сортировка `points → goal_difference → goals_for`;
- ничья разрешена;
- дисквалификация после четырёх жёлтых со сбросом;
- прямая красная и вторая жёлтая дают минимум один матч.

Длительность матча и часть специальных механик match-service в доменной модели турнира сейчас не заданы. В JSON они отмечены как `null` либо extension metadata и должны быть подтверждены до фактической миграции.

## Профиль Дворовой лиги

Профиль описывает:

- `group_stage` с тремя группами по пять команд и одним кругом;
- 30 групповых матчей;
- таблицу по регламентным критериям;
- три победителя групп и одну лучшую вторую команду;
- рейтинг вторых: очки, разница, забитые, жеребьёвка;
- посев с запретом пары второй команды с победителем её группы;
- два полуфинала, матч за третье место и финал;
- два тайма по 20 минут и пенальти без дополнительного времени;
- три жёлтые и отсутствие переноса наказаний в суперфинал.

## Проверка миграции

До включения нового read path для каждого турнира сравниваются:

- состав участников;
- количество и принадлежность матчей;
- очки и порядок таблицы;
- голы и карточки;
- активные наказания;
- ответы публичных endpoints.

Несоответствие не исправляется молча: создаётся отчёт с причиной и выбранным источником истины.
