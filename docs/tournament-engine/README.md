# Архитектурный контракт конструктора турниров

Статус: proposed  
Версия контракта: 1.0  
Область: `league-os-backend` (NestJS, TypeORM, PostgreSQL) и `league-os-frontend` (Angular)

## Назначение

Этот каталог является источником истины для поэтапного перехода от одноэтапного турнира с фиксированными правилами к универсальному конструктору. Контракт не меняет текущий runtime и не является схемой миграции. Любое последующее изменение сущностей, DTO, API или UI должно либо соответствовать этому контракту, либо сопровождаться его явным обновлением.

## Принятые решения

1. `Tournament` остаётся агрегатом внутри `Season`, но получает этапы и активную версию правил.
2. Этапы, группы, участники, матчи и права доступа являются реляционными данными.
3. Настраиваемые правила хранятся как типизированный JSONB-снимок с `schemaVersion`.
4. Пользователь выбирает только поддерживаемые типы правил и их параметры. Произвольные выражения, JavaScript, SQL и шаблонизируемый код запрещены.
5. Опубликованная версия правил неизменяема. Изменения создают новую версию.
6. Операционные результаты должны хранить версию правил, по которой они рассчитаны.
7. Текущая лига мигрирует через compatibility-профиль; одномоментное удаление старых полей не допускается.

## Нерешённые продуктовые решения

- При полном равенстве показателей Дворовой лиги требуется подтверждённый результат жеребьёвки.
- Не описанные в коде правила текущей лиги (длительность матча, дополнительное время, перенос карточек между будущими этапами) должны быть подтверждены владельцем продукта перед публикацией compatibility-профиля.
- Пользовательский конструктор первой версии поддерживает каталог известных правил, но не произвольный DSL.
