# Исправления профилей игроков

## Для управляющего командой

1. Кабинет → **Мои команды** → выбрать команду → **Состав команды**.
2. В строке игрока открыть **Действия → Профиль игрока**.
3. Фото: выбрать PNG/JPEG/WebP до 5 МБ, проверить превью и нажать **Сохранить фото**. Согласование не требуется. Фото общее для всех команд игрока.
4. ФИО / дата рождения: исправить поля, указать причину и нажать **Отправить исправление организатору**.
5. До решения действуют прежние данные. Повторная отправка заблокирована, но фото можно менять независимо.
6. После возврата прочитать комментарий и нажать **Доработать исправление**. Новый запрос сохраняет историю предыдущего рассмотрения.

Право управления определяется действующим доступом к команде, а не отметкой игрового капитана. После отзыва доступа запросы от этой команды и фото изменять нельзя.

## Для организатора

Кабинет → **Профили игроков · исправления** (`/dashboard/player-profiles`).

- Выбрать сообщество; сравнить старые и предложенные значения.
- Подтвердить исправление или вернуть с обязательным комментарием.
- При изменении даты рождения игрока из утверждённого состава турнира обязательно указать результат проверки допуска. Это не автоматическая проверка возрастного регламента: решение остаётся за организатором.
- При возможном совпадении с другой карточкой система потребует пояснения, что это разные люди. Автоматического объединения нет.
- Реестр включает действующих игроков и бывших участников команд, в том числе свободных агентов. Организатор тоже использует запрос и подтверждение.
- Для игрока, связанного с несколькими сообществами, подтвердить общую личность может только `super_admin`. Администратор сообщества может вернуть запрос с пояснением.

Изменения профиля не меняют ID/slug игрока, членство в командах, статистику, заявки и сроки дозаявок. В заявках остаются сохранённые версии. Перед подтверждённым исправлением сохраняются прежние ФИО/дата рождения в составах завершённых и подписанных игр; страницы протоколов и их события используют эти данные. Фотография остаётся актуальной. Неизвестные сведения, изменённые раньше вне этого механизма, восстановить автоматически нельзя.

Запросы и журнал доступны в контексте своего сообщества; управляющий видит запросы своей команды. Защита от повторного рассмотрения и устаревших изменений работает на сервере. Старый маршрут изменения состава больше не позволяет обходить согласование ФИО/даты рождения или журнал загрузки фото.

## Обновление базы и запуск

Нужна миграция `PlayerProfileCorrections1793836800000`: две таблицы запросов/журнала, версия личности игрока и сохранённые данные протокола. Новые параметры `.env` не нужны.

На виртуальной машине используйте существующий production Compose-проект; не запускайте корневой development Compose и не удаляйте volumes. Сначала сделайте резервную копию production БД, обновите код, затем:

```bash
cd /home/arman/league-os
docker compose --env-file .env -f infrastructure/docker/docker-compose.prod.yml build migrations backend frontend
docker compose --env-file .env -f infrastructure/docker/docker-compose.prod.yml run --rm migrations
docker compose --env-file .env -f infrastructure/docker/docker-compose.prod.yml up -d --no-deps backend frontend
docker compose --env-file .env -f infrastructure/docker/docker-compose.prod.yml ps
```

Если миграции завершились с ошибкой, не переходите к запуску новых контейнеров. Пересборки одного фронтенда недостаточно.

## Приёмочная проверка

1. Управляющий команды отправляет исправление, организатор видит старое/новое ФИО; до подтверждения публичная карточка не меняется.
2. Организатор возвращает с комментарием; управляющий дорабатывает и отправляет повторно, обе версии остаются в истории.
3. После подтверждения ID, статистика и утверждённые составы сохраняются. В старом протоколе остаётся прежнее ФИО, в текущей карточке — исправленное.
4. Проверить загрузку фото при ожидающем исправлении; новый файл получает отдельный URL. ФИО в ожидании не меняется.
5. Проверить запрет чужой команде, отозванному управляющему и обычному участнику сообщества; проверять не только скрытие кнопок, но и ответы API.
6. Два одновременно открытых профиля: после первой загрузки фото вторая загрузка со старым URL отклоняется. Повторное решение по запросу также отклоняется.
7. Изменение даты рождения допущенного игрока без пояснения проверки допуска не подтверждается. Подтверждение возможного дубля без пояснения также блокируется.

## Автоматические проверки

Сервер: `node ./node_modules/jest/bin/jest.js --runInBand --setupFiles reflect-metadata`.

Загрузка `reflect-metadata` нужна в том числе существующему изолированному тесту DTO импорта календаря. Проверки миграции на уровне SQL-команд не заменяют прогон на PostgreSQL: перед production обновлением рекомендуется применить миграцию к восстановленной копии БД.
