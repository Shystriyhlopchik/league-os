# Самостоятельная регистрация и кабинет команды

Раздел `/dashboard/my-teams` («Мои команды · создание и состав») доступен любому
зарегистрированному пользователю. Не требуется роль администратора, существующая
карточка игрока, открытый турнир или участие пользователя в игровом составе.

## Путь пользователя

1. Зарегистрироваться на сайте и войти в кабинет.
2. Проверить «Моя команда уже есть». Если команда найдена, отправить запрос
   управления с пояснением. Совпадение названия не даёт прав автоматически.
3. Для новой команды нажать «Создать команду», указать название и, при наличии,
   населённый пункт. Создаётся **непубличный черновик**, связанный с текущим
   сообществом по умолчанию. Пользователь становится владельцем команды;
   он не добавляется в `players`/игровой состав и не получает глобальную роль.
4. Заполнить карточку: полное и короткое название, город/населённый пункт,
   описание, год основания, цвета. Загрузить логотип PNG/JPEG/WebP до 5 МБ.
   Имя файла задаёт сервер. Произвольный внешний URL и SVG не принимаются.
5. Подготовить текущий состав (до 12 игроков) в этом же кабинете, независимо
   от турниров. Сначала искать существующие карточки; добавление из другой
   команды требует подтверждения перехода администратором сообщества.
6. Опубликовать карточку. Обязательны название и город либо населённый пункт.
   Логотип и описание необязательны; полный состав для публикации не требуется.
   Опубликованная команда появляется в публичном каталоге. Название и населённый
   пункт проверяются на точное совпадение с существующей опубликованной командой
   сообщества; спорные случаи решаются с администратором, без автоматического слияния.
7. Открыть «Турниры и заявки», выбрать турнир и перейти к заявке. Создать отдельную версию заявки
   турнира: до 12 игроков и до двух неиграющих представителей. Отправить на
   рассмотрение; участие возникает только после утверждения администратором.

Черновики сохраняются на сервере, и к ним можно вернуться после повторного входа.
Для защиты от массового создания ограничены три активных незавершённых команды
на создателя и десять новых команд за сутки. Созданные ранее карточки не удаляются
при повторных запросах, несовпадении версии или ошибке публикации.

## Владение и управление отдельно от игрового капитана

Права хранятся в `team_managers` с привязкой к команде и сообществу:

| Назначение | Возможности |
| --- | --- |
| Владелец (`owner`) | Карточка, состав, заявки; выдача и отзыв управления |
| Управляющий (`manager`) | Карточка, состав и заявки, без выдачи прав другим |
| Администратор/владелец сообщества | Управление командами и запросами доступа своего сообщества |

Это не глобальные `user_roles` и не роли турнира. `team_players.isCaptain`
обозначает только игрового капитана. Смена этой отметки не выдаёт и не отзывает
управление. Владелец может быть неиграющим; его исключение из игрового состава
не лишает команду управления. Представители заявки остаются только неиграющими
записями и не получают никаких полномочий автоматически.

В разделе «Доступ» владелец вводит точный логин уже зарегистрированного
пользователя, чтобы добавить управляющего. Назначение владельца вынесено в отдельный
блок «Управление владением» и требует подтверждения. Для передачи владения сначала назначается новый
владелец, затем снимается старое назначение. Нельзя удалить или понизить последнего
активного владельца. Создатель после отзыва назначения не имеет скрытого обхода
проверок через `created_by_user_id`.

При исключении из сообщества доступ к команде блокируется, включая управление
назначениями. Восстановление членства может восстановить сохранённые назначения;
если права нужно отозвать окончательно, их следует снять отдельно. Отключённые
учётные записи и исключённые участники не считаются действующим преемником
при проверке последнего владельца. Администратор сообщества может назначить
нового активного владельца для восстановления управления.

## Доступ к существующей команде

Пользователь находит опубликованную команду и отправляет запрос с пояснением
своей связи с ней. В кабинете администратора сообщества отображаются ФИО, логин,
команда и пояснение — без паролей, email и телефона из учётной записи.

Администратор проверяет полномочия вручную и подтверждает либо отказывает
с обязательным комментарием. Если действующий владелец уже есть, подтверждение
выдаёт роль управляющего; если владельца нет — владельца. Повторно рассмотреть
уже обработанный запрос нельзя. История назначений и решений сохраняется
в `team_management_audit`. Владелец команды не подменяет администратора при
рассмотрении таких запросов; он может выдать права отдельно, по точному логину.

## Совместимость и миграция

Новая миграция: `1792627200000-team-self-service.ts`, после миграций сообществ
и турнирных заявок. Существующие команды остаются опубликованными.

Для действующих старых капитанов, связанных с активной учётной записью,
миграция однократно создаёт независимые назначения:

- Если такой капитан у команды один, он получает владение.
- Если их несколько, все сохраняют управление, но владельца должен выбрать
  администратор сообщества. Миграция не выбирает его произвольно.
- Если связанной учётной записи нет, после регистрации нужен запрос управления
  либо назначение администратором. Простого совпадения ФИО/отметки капитана
  недостаточно для захвата команды.

Сделайте и проверьте резервную копию PostgreSQL по README. Далее используйте
обычную процедуру обновления с пересборкой `migrations`, `backend`, `frontend`:

```bash
cd /home/arman/league-os
git pull --ff-only
docker compose --env-file .env -p league-os-prod -f infrastructure/docker/docker-compose.prod.yml build migrations backend frontend
docker compose --env-file .env -p league-os-prod -f infrastructure/docker/docker-compose.prod.yml stop backend frontend
docker compose --env-file .env -p league-os-prod -f infrastructure/docker/docker-compose.prod.yml run --rm migrations
# Продолжайте только после успешной миграции:
docker compose --env-file .env -p league-os-prod -f infrastructure/docker/docker-compose.prod.yml up -d backend frontend
```

Не меняйте имя существующего Compose-проекта и не используйте `down -v`.
При новом развёртывании сначала применяются все предыдущие миграции и их проверки
связей игроков. Автоматического отката с удалением владельцев/истории нет:
откат выполняется из резервной копии с совместимой версией приложения.

Загрузка логотипов использует уже существующий volume `uploads_data` и маршрут
`/uploads/teams/`. Отдельного изменения Nginx при действующем проксировании
`/uploads` не требуется. Не копируйте произвольные пути из имени файла пользователя.

Профили имеют `profile_version`: сохранение из устаревшей вкладки возвращает
409, не перезаписывая чужие изменения. В интерфейсе есть «Обновить с сервера»;
при наличии несохранённых данных потребуется подтверждение. Отказ оставляет
поля без изменений. Загрузка логотипа сохраняется отдельно и не сохраняет
текстовые поля карточки.

## Навигация и ручная проверка интерфейса

У нового пользователя сначала два пути: создать команду либо запросить доступ
к существующей. Одновременно открывается только одна форма. У пользователя
с командой первым открывается **«Состав»**. Остальные разделы — **«О команде»**,
**«Турниры и заявки»**, **«Доступ»**; последний виден только при наличии полномочий.
Администратор рассматривает запросы управления командами в **«Сообществах»**
(`/dashboard/communities`), а не среди повседневных действий капитана.

Проверьте на настольном экране и на телефоне:

1. Новый пользователь: нет пустого выбора команды и нескольких раскрытых форм.
   Создание черновика переводит к составу, но не добавляет владельца в игроки.
2. «Добавить игрока»: сначала поиск; после поиска доступно создание карточки.
   Игрок другой команды добавляется через запрос перехода. Список ограничен 12,
   и это максимум, а не требование заполнить все места.
3. «Действия» у игрока: номер и капитан меняются одной формой; исключение требует
   подтверждения с именем и предупреждением о неизменности утверждённых заявок.
4. «О команде»: сначала просмотр, затем явное редактирование. После изменения
   описания переключитесь между разделами — текст должен сохраниться в форме.
   При смене команды, уходе со страницы или обновлении вкладки есть предупреждение.
   Отказ от потери изменений оставляет данные и выбранную команду на месте.
5. Загрузите логотип при несохранённом описании: логотип меняется сразу, описание
   остаётся несохранённым. Вторая вкладка со старой версией не может затереть изменения.
6. Публикация карточки не утверждает заявку на турнир. В «Турнирах и заявках»
   отображаются реальные состояния: черновик, рассмотрение, доработка, утверждение.
   Ошибка получения статуса не показывается как отсутствие заявки.
7. Управляющий не видит выдачу доступа; владелец видит. Отзыв требует подтверждения
   с именем, последний активный владелец защищён. Назначение ещё одного владельца
   не отзывает прежние права автоматически и не понижает владельца через форму
   добавления управляющего.
8. В «Сообществах» комментарий отказа относится к конкретному запросу. При смене
   сообщества запоздалый ответ предыдущего сообщества не заменяет текущий список.

Модель подготовлена к нескольким сообществам, но создание команд пока использует
сообщество по умолчанию; это не полная изоляция всех старых глобальных разделов.

## Проверки разработчиком

`src/database/verify-team-workspace.ts` проверяет настоящий HTTP-сценарий регистрации
и работу миграции на старой команде. Использует только одноразовую БД
`admissions_test` на `127.0.0.1:55439` (как сценарий проверки заявок), а логотипы
пишет в отдельный временный каталог и удаляет после проверки:

```bash
docker run --rm -d --name league-os-applications-test -e POSTGRES_USER=admissions_test -e POSTGRES_PASSWORD=isolated_test_only -e POSTGRES_DB=admissions_test -p 127.0.0.1:55439:5432 postgres:16-alpine
# Из league-os-backend:
node -r ts-node/register -r tsconfig-paths/register src/database/verify-team-workspace.ts
node -r ts-node/register -r tsconfig-paths/register src/database/verify-tournament-applications.ts
docker stop league-os-applications-test
```
