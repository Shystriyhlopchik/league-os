# Анонсы новостей во ВКонтакте

## Возможности первой версии

Редактор `/dashboard/new-news` сохраняет статью для сайта и отдельный анонс ВК:
заголовок, текст и необязательное изображение JPEG/PNG до 5 МБ. Обложку статьи
можно использовать повторно. WebP поддерживается для сайта, но не для отправки
через этот коннектор.

Администратор сначала публикует статью на сайте, затем отдельно подтверждает
отправку анонса. Ссылка на статью и UTM-метки добавляются сервером. Изменения
статьи или анонса после отправки не редактируют внешний пост.

Новости теперь принадлежат сообществам. Управление доступно владельцу и
администратору соответствующего сообщества, а также `super_admin` платформы.
Обычная глобальная роль `admin` без членства не даёт доступ к чужим новостям.
Миграция переносит старые новости в сообщество с `"isDefault" = true`.

В этой версии сервер подключает **одну пару «сообщество сайта — группа ВК»**.
Для остальных сообществ подготовка анонсов работает, отправка отключена.
Telegram, отложенная публикация, удаление и редактирование внешних постов,
полноценный rich-text редактор и самостоятельное подключение через OAuth в
интерфейсе не входят в эту версию.

## Подготовка ВК

1. Уточните числовой ID сообщества ВК, в котором нужно публиковать новости.
2. Получите пользовательский токен через разрешённый ВК способ авторизации
   вашего приложения, поддерживающий необходимые операции со стеной и фото.
   Пользователь должен иметь права редактора/администратора выбранной группы.
   Совместимость типа приложения и выдаваемых разрешений нужно проверить на
   стороне ВК: наличие административной роли само по себе не выдаёт API-доступ.
3. Не используйте сторонние сайты для получения токенов и не передавайте токен
   в чат, URL, исходники Angular или Git. В опубликованной схеме ВК методы
   `wall.post`, `photos.getWallUploadServer`, `photos.saveWallPhoto` используют
   пользовательский тип токена; обычный ключ сообщества нельзя считать заменой.

Первичные источники:

- [Схема методов wall](https://raw.githubusercontent.com/VKCOM/vk-api-schema/master/wall/methods.json).
- [Схема методов photos](https://raw.githubusercontent.com/VKCOM/vk-api-schema/master/photos/methods.json).

## Настройки сервера

В корневом `.env`, который подключает production Compose:

```dotenv
FRONTEND_URL=https://liga-dvora.ru
VK_PUBLISHING_ENABLED=true
VK_NEWS_COMMUNITY_ID=1
VK_GROUP_ID=123456789
VK_ACCESS_TOKEN=replace_with_authorized_user_token
VK_API_VERSION=5.199
```

`1` и `123456789` — примеры, замените их реальными значениями. `VK_GROUP_ID`
положительный, без минуса; `VK_NEWS_COMMUNITY_ID` — ID сообщества **в нашей БД**,
не ID группы ВК и не турнира. Уточнить ID можно в кабинете при выборе сообщества
(запрос `/api/admin/news/communities`) или через read-only SQL:

```sql
SELECT id, name, "isDefault" FROM communities WHERE "isActive" = true;
```

Без корректных настроек отправка отключена, но редактор и подготовка анонсов
доступны. Токен не возвращается API. Проверка подключения обращается только к
`groups.getById`, не создаёт постов и не гарантирует, что приложению разрешена
запись на стене: это подтверждается только реальной отправкой.

## Развёртывание

Сначала сделайте резервную копию БД, `.env` и `uploads` по основной инструкции
деплоя. Обновляйте только проект `league-os-prod`, не соседний `sportcheb-prod`.
Не удаляйте тома и не используйте `down -v`.

После получения нужного коммита выполните из `/home/arman/league-os`:

```bash
docker compose --env-file .env -p league-os-prod \
  -f infrastructure/docker/docker-compose.prod.yml build migrations backend frontend

docker compose --env-file .env -p league-os-prod \
  -f infrastructure/docker/docker-compose.prod.yml run --rm migrations

docker compose --env-file .env -p league-os-prod \
  -f infrastructure/docker/docker-compose.prod.yml up -d --no-build backend frontend

docker compose --env-file .env -p league-os-prod \
  -f infrastructure/docker/docker-compose.prod.yml ps
```

Нужна миграция `NewsVkPublication1792972800000`: новые поля новости и таблица
`news_publications`. Backend нельзя обновлять без миграции. Frontend тоже
пересобирается: изменены редактор и nginx. Если менялись только настройки `.env`,
пересоздайте backend и nginx frontend с `up -d --no-deps --force-recreate backend frontend` с теми же
`--env-file`, `-p` и `-f`; простой `restart` не перечитывает переменные контейнера.

## Проверка после запуска

1. Откройте «Написать новость», выберите нужное сообщество и создайте черновик.
2. Убедитесь, что его публичный адрес недоступен, а отправка ВК заблокирована.
3. Заполните отдельный анонс, загрузите JPEG/PNG, сохраните статью и опубликуйте её.
4. В блоке ВК проверьте адрес подключённой группы и нажмите
   «Проверить подключение без публикации».
5. Убедитесь, что картинка открывается по публичному HTTPS-адресу без 403.
6. Проверьте индивидуальное превью ссылки, например:

```bash
curl -fsS https://liga-dvora.ru/news/actual-article-slug | \
  grep -oE '<meta property="og:[^"]+"[^>]*>'
```

7. Только когда готовы к **реальной публикации**, нажмите «Отправить анонс в ВК»
   и подтвердите действие. Должны появиться статус и ссылка на созданный пост.
8. Проверьте ссылку из поста, фотографию, текст и отсутствие второго поста после
   обновления редактора. Без токена и явной отправки тестовые посты не создаются.

Production nginx передаёт `/news/:slug` в `/api/news/:slug/page`. Backend берёт
Angular-шаблон из `http://frontend/index.html` и вставляет метаданные конкретной
статьи в первоначальный HTML. Эта внутренняя настройка задаётся Compose через
`NEWS_HTML_TEMPLATE_URL`. После появления новой статьи пересборка не нужна.
При иной топологии настройте доступный backend внутренний URL шаблона; запрос
не должен вести обратно на `/news/:slug`, иначе возникнет цикл. Это не SSR всего
приложения: содержимое статьи по-прежнему отображает Angular. Локальный `ng serve`
не использует production nginx-маршрут метаданных.

Внешняя карточка ссылки использует заголовок/краткое описание/обложку **статьи**;
изображение и текст **анонса** отправляются в сам пост. ВК может кэшировать
карточку ссылки и отображать её иначе, чем локальный предпросмотр.

## Ошибки и повторная отправка

- Очередь хранится в PostgreSQL. Worker внутри backend проверяет её каждые 5 секунд.
  Внешние запросы не выполняются внутри транзакции с блокировкой очереди.
- На одну статью допускается один анонс ВК. Повторный клик возвращает существующее
  задание, а не создаёт новый пост. Снимок текста, изображения, назначения, ссылки
  и `guid` сохраняется при первой отправке.
- Явные временные отказы безопасно повторяются с задержкой, максимум до трёх
  автоматических попыток. Постоянная ошибка требует исправления и ручного повтора.
- При тайм-ауте `wall.post` неизвестно, создал ли ВК пост. Статус становится
  «Результат отправки не подтверждён», автоматического повтора нет. Незавершённая
  отправка после перезапуска получает этот статус через три минуты.
- **Сначала проверьте стену сообщества.** Повтор допустим только если поста нет.
  Используется прежний `guid`, но абсолютную гарантию exactly-once внешний API
  не даёт. Нельзя нажимать повтор «на всякий случай».
- Повтор использует прежний текст и картинку, даже если поля редактора уже изменены.
  Смена группы/сообщества в `.env` не перенаправляет старые задания автоматически.
- Если статья снята с публикации или удалена до начала отправки, задание завершается
  ошибкой. Уже созданный пост не удаляется. При снятии статьи с публикации её ссылка
  станет недоступна; интерфейс предупреждает об этом.
- После первой публикации slug статьи фиксируется, в том числе после снятия с
  публикации. Заголовок, содержание и обложку менять можно.

Для диагностики безопаснее смотреть статус в редакторе и сообщения backend.
Не выводите целиком `.env`, Docker `Config.Env` или исходные ответы ВК: в них
могут оказаться секреты. В приложении сохраняются только обезличенные сообщения
об ошибках, ID автора отправки и последнего инициатора повтора, число попыток и
подтверждённая ссылка на пост.
