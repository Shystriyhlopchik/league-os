# Анонсы новостей во ВКонтакте

## Возможности первой версии

Редактор `/dashboard/new-news` сохраняет статью для сайта и отдельный анонс ВК:
заголовок, текст и необязательное изображение карточки ссылки JPEG/PNG до 5 МБ.
Обложку статьи можно использовать повторно. Изображение хранится на нашем сайте:
в ВК отправляется **текст с кликабельной ссылкой, без вложений**. Параметры
`attachments` и `link_photo_id` не передаются, методы `photos.getWallUploadServer`
и `photos.saveWallPhoto` не вызываются. Изображение остаётся в Open Graph
метаданных сайта; картинка-превью в посте ВК не гарантируется.

Администратор сначала публикует статью на сайте, затем отдельно подтверждает
отправку анонса. Ссылка на статью и UTM-метки добавляются сервером. Изменения
статьи или анонса после отправки не редактируют внешний пост.

Новости теперь принадлежат сообществам. Управление доступно владельцу и
администратору соответствующего сообщества, а также `super_admin` платформы.
Обычная глобальная роль `admin` без членства не даёт доступ к чужим новостям.
Миграция переносит старые новости в сообщество с `"isDefault" = true`.

В этой версии сервер подключает **одну пару «сообщество сайта — группа ВК»**.
Для остальных сообществ подготовка анонсов работает, отправка отключена.
Telegram, отложенная публикация, удаление и редактирование внешних постов,
полноценный rich-text редактор и самостоятельное подключение через OAuth в
интерфейсе не входят в эту версию.

## Подготовка ВК

1. Уточните числовой ID сообщества ВК, в котором нужно публиковать новости.
2. В настройках именно этого сообщества откройте «Работа с API → Ключи доступа»
   и создайте ключ с разрешением `wall` (доступ к стене). В нашем сценарии права
   `photos`, `messages` и `stories` не требуются. Уже выданный ключ с дополнительными
   правами можно использовать; перевыпуск не обязателен.
3. Сохраните ключ в серверный `.env`. Не используйте сторонние сайты для получения
   токенов и не передавайте ключ в чат, URL, исходники Angular или Git.
4. Проверьте подключение без публикации, затем при готовности явно подтвердите
   одну реальную отправку. Наличие `wall` не гарантирует, что конкретный ключ
   может публиковать в выбранную группу: окончательный результат даёт `wall.post`.
   В опубликованной схеме метода указан пользовательский тип токена, поэтому
   совместимость с ключом сообщества нельзя объявлять проверенной до реальной
   отправки. Приложение корректно покажет отказ ВК, если запись не разрешена.

Ранее выданные совместимые пользовательские токены также поддерживаются:
если метод прав сообщества отклоняет тип ключа с кодом 27/28, проверяются
`is_admin` и `admin_level` пользователя. Сетевые ошибки, код 5 и отсутствие
разрешения `wall` не обходятся этим резервным механизмом.

Первичные источники:

- [Схема методов wall](https://raw.githubusercontent.com/VKCOM/vk-api-schema/master/wall/methods.json).
- [Схема методов groups](https://raw.githubusercontent.com/VKCOM/vk-api-schema/master/groups/methods.json).

## Настройки сервера

В корневом `.env`, который подключает production Compose:

```dotenv
FRONTEND_URL=https://liga-dvora.ru
VK_PUBLISHING_ENABLED=true
VK_NEWS_COMMUNITY_ID=1
VK_GROUP_ID=123456789
VK_ACCESS_TOKEN=replace_with_community_access_token
VK_API_VERSION=5.199
```

`1` и `123456789` — примеры, замените их реальными значениями. `VK_GROUP_ID`
положительный, без минуса; `VK_NEWS_COMMUNITY_ID` — ID сообщества **в нашей БД**,
не ID группы ВК и не турнира. Уточнить ID можно в кабинете при выборе сообщества
(запрос `/api/admin/news/communities`) или через read-only SQL:

```sql
SELECT id, name, "isDefault" FROM communities WHERE "isActive" = true;
```

Без корректных настроек отправка отключена, но редактор и подготовка анонсов
доступны. Токен не возвращается API. Проверка подключения вызывает
`groups.getTokenPermissions` (для ключа сообщества требуется бит `wall`, 8192)
и `groups.getById`. Она не требует полей `is_admin`/`admin_level` от ключа
сообщества и не создаёт постов. Публичная информация о выбранной группе сама по
себе не подтверждает принадлежность ключа этой группе. Успешная проверка означает
доступность группы и разрешение ключа, но не доказанную возможность записи;
ответ такой проверки содержит `publicationVerified: false`. Подтверждение
реальной публикации хранится отдельно — в статусе задания и ссылке на пост.

## Развёртывание

Сначала сделайте резервную копию БД, `.env` и `uploads` по основной инструкции
деплоя. Обновляйте только проект `league-os-prod`, не соседний `sportcheb-prod`.
Не удаляйте тома и не используйте `down -v`.

После получения нужного коммита выполните из `/home/arman/league-os`:

```bash
docker compose --env-file .env -p league-os-prod \
  -f infrastructure/docker/docker-compose.prod.yml build migrations backend frontend

docker compose --env-file .env -p league-os-prod \
  -f infrastructure/docker/docker-compose.prod.yml run --rm migrations

docker compose --env-file .env -p league-os-prod \
  -f infrastructure/docker/docker-compose.prod.yml up -d --no-build backend frontend

docker compose --env-file .env -p league-os-prod \
  -f infrastructure/docker/docker-compose.prod.yml ps
```

Нужна миграция `NewsVkPublication1792972800000`: новые поля новости и таблица
`news_publications`. Backend нельзя обновлять без миграции. Frontend тоже
пересобирается: изменены редактор и nginx. Если менялись только настройки `.env`,
пересоздайте backend и nginx frontend с `up -d --no-deps --force-recreate backend frontend` с теми же
`--env-file`, `-p` и `-f`; простой `restart` не перечитывает переменные контейнера.

Если эта миграция уже применена и вы переходите с прежнего режима «пост + фото»
на «текст + ссылка», **новая миграция и новые переменные не нужны**. Пересоберите
backend и frontend, сохранив текущие ID и ключ сообщества. Старые задания не
удаляются и не отправляются повторно автоматически; при ручном повторе вместо
фотовложения отправится сохранённый текст со ссылкой, без `attachments`.
Для статуса `unknown` сначала
обязательно проверьте стену, как описано ниже.

## Проверка после запуска

1. Откройте «Написать новость», выберите нужное сообщество и создайте черновик.
2. Убедитесь, что его публичный адрес недоступен, а отправка ВК заблокирована.
3. Заполните отдельный анонс, загрузите JPEG/PNG, сохраните статью и опубликуйте её.
4. В блоке ВК проверьте адрес подключённой группы и нажмите
   «Проверить подключение без публикации».
5. Убедитесь, что картинка открывается по публичному HTTPS-адресу без 403.
6. Проверьте индивидуальное превью ссылки, например:

```bash
curl -fsS https://liga-dvora.ru/news/actual-article-slug | \
  grep -oE '<meta property="og:[^"]+"[^>]*>'
```

7. Только когда готовы к **реальной публикации**, нажмите «Отправить анонс в ВК»
   и подтвердите действие. Должны появиться статус и ссылка на созданный пост.
8. Проверьте кликабельную ссылку из поста, текст и отсутствие второго поста после
   обновления редактора. Без токена и явной отправки тестовые посты не создаются.
   Не ожидайте обязательной карточки или фотографии: они не прикрепляются.

Production nginx передаёт `/news/:slug` в `/api/news/:slug/page`. Backend берёт
Angular-шаблон из `http://frontend/index.html` и вставляет метаданные конкретной
статьи в первоначальный HTML. Эта внутренняя настройка задаётся Compose через
`NEWS_HTML_TEMPLATE_URL`. После появления новой статьи пересборка не нужна.
При иной топологии настройте доступный backend внутренний URL шаблона; запрос
не должен вести обратно на `/news/:slug`, иначе возникнет цикл. Это не SSR всего
приложения: содержимое статьи по-прежнему отображает Angular. Локальный `ng serve`
не использует production nginx-маршрут метаданных.

Метаданные страницы содержат `og:title` из заголовка анонса (если он пуст —
из заголовка статьи), `og:description` из текста анонса (до 500 символов, иначе
из описания/текста статьи), `og:image` из изображения карточки. Если оно не
выбрано, используется обложка статьи; если нет и обложки — фото лиги.
Публичная статья сохраняет собственные заголовок, текст и обложку.
Изображение и сама статья должны быть доступны без авторизации. Эти метаданные
могут использоваться сервисами, поддерживающими предпросмотр ссылок, но сами по
себе не обеспечивают картинку в посте ВК. Принудительное вложение ссылки отключено:
ВК отклонял его с `link_photo_sizing_rule. No photo given`, несмотря на
наличие страницы. Ссылка остаётся частью текста анонса.

## Ошибки и повторная отправка

- Очередь хранится в PostgreSQL. Worker внутри backend проверяет её каждые 5 секунд.
  Внешние запросы не выполняются внутри транзакции с блокировкой очереди.
- На одну статью допускается один анонс ВК. Повторный клик возвращает существующее
  задание, а не создаёт новый пост. Снимок текста, выбранного изображения, назначения, ссылки
  и `guid` сохраняется при первой отправке.
- Явные временные отказы безопасно повторяются с задержкой, максимум до трёх
  автоматических попыток. Постоянная ошибка требует исправления и ручного повтора.
- При тайм-ауте `wall.post` неизвестно, создал ли ВК пост. Статус становится
  «Результат отправки не подтверждён», автоматического повтора нет. Незавершённая
  отправка после перезапуска получает этот статус через три минуты.
- **Сначала проверьте стену сообщества.** Повтор допустим только если поста нет.
  Используется прежний `guid`, но абсолютную гарантию exactly-once внешний API
  не даёт. Нельзя нажимать повтор «на всякий случай».
- Повтор использует прежний текст и ссылку, даже если поля редактора уже изменены.
  Сохранённый путь картинки остаётся для истории, но не передаётся в фотометоды ВК.
  Метаданные страницы остаются текущими и не являются снимком задания.
  Смена группы/сообщества в `.env` не перенаправляет старые задания автоматически.
- Если статья снята с публикации или удалена до начала отправки, задание завершается
  ошибкой. Уже созданный пост не удаляется. При снятии статьи с публикации её ссылка
  станет недоступна; интерфейс предупреждает об этом.
- После первой публикации slug статьи фиксируется, в том числе после снятия с
  публикации. Заголовок, содержание и обложку менять можно.
- Код 27 означает отказ авторизации сообщества/несовместимость метода с ключом,
  а не обязательно истёкший токен. Код 28 относится к авторизации приложения.
  Для этих ошибок больше не выводится совет безусловно перевыпустить токен.
- Для кода 100 показывается метод запроса, например `wall.post`, и распознанное
  имя неверного параметра с пояснением на русском. Если перевод не распознан,
  сохраняется и показывается очищенное текстовое уточнение ВК (до 500 символов).
  Ключ доступа, его URL/form-encoded представления, длинные значения запроса,
  ссылки, значения в кавычках и похожие на токены строки скрываются до обрезки.
  `request_params` не читается и не сохраняется; встроенный в текст дамп также
  скрывается. Если ВК вернул только общее пояснение, оно будет показано буквально
  после очистки — это не означает, что конкретный неверный параметр уже установлен.
  Если текстового уточнения нет, интерфейс явно сообщает об этом.
  Это диагностика, а не автоматическое исправление параметров: код 100
  останавливает задание без автоматических повторов.

### Обновление диагностики кода 100

Новых миграций и изменений frontend для этой правки нет. После переноса коммита
на сервер пересоберите только backend из каталога `/home/arman/league-os`:

```bash
docker compose --env-file .env -f infrastructure/docker/docker-compose.prod.yml build backend
docker compose --env-file .env -f infrastructure/docker/docker-compose.prod.yml up -d --no-deps backend
docker compose --env-file .env -f infrastructure/docker/docker-compose.prod.yml ps backend
```

Старая сохранённая ошибка не изменится от перезапуска. Проверьте отсутствие поста
на стене сообщества, затем в редакторе используйте повторную отправку существующего
задания. **Повтор — настоящая публикация**, если ВК примет запрос. Если отказ
повторится, передайте новое сообщение целиком из интерфейса, без токена.

### Исправление `link_photo_sizing_rule. No photo given`

После переноса этой правки на сервер пересоберите backend и frontend
(в редакторе обновлены пояснения). Новых миграций и переменных окружения нет.
Из `/home/arman/league-os`:

```bash
docker compose --env-file .env -p league-os-prod \
  -f infrastructure/docker/docker-compose.prod.yml build backend frontend
docker compose --env-file .env -p league-os-prod \
  -f infrastructure/docker/docker-compose.prod.yml up -d --no-deps backend frontend
docker compose --env-file .env -p league-os-prod \
  -f infrastructure/docker/docker-compose.prod.yml ps backend frontend
```

Не удаляйте существующее задание и не меняйте его `guid`. Задания со статусом
`failed` сами повторно не отправляются. Проверьте отсутствие поста на стене и
в редакторе нажмите повторную отправку: будут использованы прежние текст,
ссылка и `guid`, но ссылка больше не передаётся отдельным вложением.
Это реальная публикация, а не проверка подключения. При статусе `unknown`
также требуется явное подтверждение отсутствия поста.

Для диагностики безопаснее смотреть статус в редакторе и сообщения backend.
Не выводите целиком `.env`, Docker `Config.Env` или исходные ответы ВК: в них
могут оказаться секреты. В приложении сохраняются только обезличенные сообщения
об ошибках, ID автора отправки и последнего инициатора повтора, число попыток и
подтверждённая ссылка на пост.
